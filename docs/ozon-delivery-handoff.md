## 2. Авторизация: что выяснено

### Хост

```
POST https://xapi.ozon.ru/oauth/token
```

**Не** `api-seller.ozon.ru` — там `/oauth/*` отдаёт 403 от антибота, что легко
принять за «путь есть, но закрыт». На эту ловушку уже потрачено время.

Сам API доставки живёт на `https://api-seller.ozon.ru`, токен передаётся
заголовком `Authorization: Bearer <access_token>`.

### grant_type: client_credentials НЕ РАБОТАЕТ

```
400 {"code":3,"message":"scope 'seller-app-store-api.payment' is not approved"}
```

Ozon выдаёт токен сразу на все скоупы приложения и спотыкается на неодобренном
`seller-app-store-api.payment`. Этого скоупа нет в списке выбираемых в кабинете
— снять его невозможно. Параметр `scope` в запросе принимается, но игнорируется
(проверено с несуществующим и с корректным значением — ошибка одна и та же).

Проверено и с локальной машины, и с сервера, чей IP в белом списке приложения:
результат одинаковый. Дело не в IP.

### grant_type: authorization_code РАБОТАЕТ

Ключ к обходу — из документации Applications API:

> Если скоупы ролей в частном приложении и в ссылке на авторизацию отличаются,
> доступ будет выдан только для ролей из ссылки.

Права берутся из ссылки, поэтому неодобренный скоуп в неё не попадает.

**Ссылка авторизации** (открывать в браузере с активной сессией кабинета
продавца):

```
https://seller.ozon.ru/app/appstore/oauth/authorize
  ?response_type=code
  &access_type=offline
  &client_id=<OZON_CLIENT_ID>
  &redirect_uri=https%3A%2F%2Fclc-ufa.ru%2Fapi%2Fozon%2Fcallback
  &scope=seller-api.ozon-logistics
  &state=<случайная строка>
```

`access_type=offline` обязателен — без него не вернётся `refresh_token`.

**Обмен кода на токены:**

```jsonc
POST https://xapi.ozon.ru/oauth/token
{
  "client_id":     "...",
  "client_secret": "...",
  "grant_type":    "authorization_code",
  "code":          "<код из redirect_uri>",
  "redirect_uri":  "https://clc-ufa.ru/api/ozon/callback"
}
```

Ответ: `access_token`, `refresh_token`, `token_type`, `scope`, `expires_in`.

**Обновление** — тем же методом с `grant_type: "refresh_token"` и полем
`refresh_token`.

### ⚠️ expires_in — это АБСОЛЮТНАЯ МЕТКА ВРЕМЕНИ, а не длительность

Проверено: пришло `1786703183`, что соответствует `2026-08-14T10:26:23Z`, то
есть примерно час от момента выдачи.

Код вида `Date.now() + expires_in * 1000` решит, что токен живёт 56 лет, и
никогда его не обновит. Обновляйте с запасом: считайте токен протухшим за
минуту до `expires_in * 1000`.

## 3. Текущее состояние токенов

Пара токенов уже получена и лежит на сервере:

```
/root/ozon-tokens.json   (права 600, владелец root)
```

Скоуп в ответе: `["seller-api.ozon-logistics"]` — ровно нужный.

**Это временное место.** Приложение работает от пользователя `clcufa` и прочитать
файл не может. Нужно перенести (см. следующий раздел).

**Refresh-токен беречь.** Если он потеряется, восстановить доступ можно только
ручным подтверждением владельца в браузере по ссылке выше. Автоматически —
никак.

## 4. Где хранить токены

Задача нетипичная для этого проекта: у сайта нет базы данных и он ничего не
пишет на диск. Здесь состояние необходимо.

Ограничения сервера:

- служба `clc-ufa.service` работает от пользователя `clcufa`;
- юнит защищён (`ProtectHome`, `ProtectKernel*`, `CapabilityBoundingSet=` и др.);
- на запись разрешён единственный путь: `ReadWritePaths=/var/www/clc-ufa/.next/cache`;
- **этот каталог стирается при каждом деплое** — хранить токены там нельзя.

**Предлагаемое решение:**

```bash
mkdir -p /var/lib/clc-ufa
chown clcufa:clcufa /var/lib/clc-ufa
chmod 700 /var/lib/clc-ufa
mv /root/ozon-tokens.json /var/lib/clc-ufa/ozon-tokens.json
chown clcufa:clcufa /var/lib/clc-ufa/ozon-tokens.json
chmod 600 /var/lib/clc-ufa/ozon-tokens.json
```

В юнит добавить (не ослабляя остальных ограничений):

```ini
ReadWritePaths=/var/www/clc-ufa/.next/cache /var/lib/clc-ufa
```

Затем `systemctl daemon-reload && systemctl restart clc-ufa`.

Путь вынести в переменную `OZON_TOKEN_FILE` (значение по умолчанию —
`/var/lib/clc-ufa/ozon-tokens.json`), чтобы локальная разработка не упиралась в
серверный путь.

**Запись должна быть атомарной**: писать во временный файл рядом и переименовывать.
Иначе одновременные запросы могут покалечить файл, и refresh-токен будет потерян
безвозвратно.

## 5. Методы API: что проверено

Проверялось с сервера, токеном с единственным скоупом `seller-api.ozon-logistics`.

| Метод | Результат |
|---|---|
| `POST /v1/delivery/point/list` | **200**, вернул массив `points` с `map_point_id` и `coordinate` |
| `POST /v2/delivery/checkout` | 400: `invalid DeliveryCheckoutRequestV2.Items: value must contain between 1 and 1000 items` |
| `POST /v1/delivery/check` | 400: `ClientPhone: value does not match regex "^\d{10,15}$"` |
| `POST /v1/seller/ozon-logistics/info` | сетевая ошибка при проверке, повторить |

Ошибки 400 — это валидация схемы, то есть доступ есть, не хватает полей.

**Схемы запросов не выяснены** — это первая задача. Документация:
`https://docs.ozon.ru/api/seller/` → раздел про Ozon Доставку. Открывается
**только браузером**: обычный HTTP-загрузчик уходит в петлю редиректов.

Пустой ответ `point/list` содержал только идентификаторы и координаты, без
адресов. Вероятно, адреса даёт `/v1/delivery/point/info`, либо нужен фильтр по
городу — уточните по документации.

Полный список 19 доступных методов — в `seller-api.ozon-logistics`:
`/v1/delivery/checkout`, `/v2/delivery/checkout`, `/v1/delivery/point/list`,
`/v1/delivery/point/info`, `/v1/delivery/map`, `/v1/delivery/check`,
`/v1/order/create`, `/v2/order/create`, `/v1/order/cancel`, `/v1/posting/cancel`,
`/v1/posting/marks`, `/v1/cancel-reason/*`, `/v1/seller/ozon-logistics/info`,
`/v1/seller/ozon-logistics/connect` и другие.

**Создание заказов не подключать.** Нужны только расчёт и пункты выдачи; накладные
оформляются в кабинете. Так же сделано у СДЭК и по той же причине: без базы данных
у сайта нет надёжного следа о созданном отправлении.

## 6. Что именно реализовать

### `lib/delivery/ozon.ts`

Реализовать интерфейс `DeliveryProvider`:

```ts
isConfigured(): boolean
quotes(city: string, parcel: Parcel, destination?: DeliveryDestination): Promise<DeliveryQuote[]>
points(city: string): Promise<PickupPoint[]>
```

- `isConfigured()` — `true`, только если есть ключи **и** доступен refresh-токен.
  Пока чего-то нет, возвращать `false`: сайт тогда честно показывает «стоимость
  сообщит менеджер», и оформление не ломается. Это уже работает, не сломайте.
- Токен получать лениво и кэшировать в памяти процесса, обновляя по
  `refresh_token` (см. предупреждение про `expires_in`).
- Разбор ответов делать устойчивым к отсутствующим полям — как `toQuote()` и
  `toPoint()` в `cdek.ts`.
- Города: у СДЭК потребовался справочник `location/cities`. Как задаётся город у
  Ozon — выяснить; возможно, достаточно координат или кода населённого пункта.

### Фильтрация по способу получения

`destination` уже есть в интерфейсе. У СДЭК отбор идёт по `delivery_mode`
(см. `matchesDestination()`). У Ozon механизм свой — если тарифы делятся на «до
двери» и «в пункт выдачи», отфильтруйте аналогично.

Важно: покупатель, выбравший ПВЗ, не должен видеть курьерские тарифы. Это уже
исправляли для СДЭК, не повторяйте ошибку.

### Тесты

`tests/delivery-providers.test.ts` содержит проверку, что Ozon помечен как
неготовый:

```ts
assert.equal(providers.ozon.isConfigured(), false)
```

Её нужно будет обновить. Добавьте тесты на разбор ответов и на пересчёт
`expires_in` — второе важнее всего: ошибка там тихая и проявится через час
работы, а не сразу.

## 7. Ограничения проекта

- **CSP запрещает браузеру ходить на сторонние хосты.** Все обращения к Ozon —
  только с сервера, через существующие роуты `/api/delivery/*`. Не добавляйте
  виджеты и внешние скрипты: `next.config.js` их заблокирует.
- **Ключи не должны попадать в клиентский бандл.** Никаких `NEXT_PUBLIC_`.
- **Переменные окружения на сервере — в `/etc/clc-ufa/env`**, не в `.env.local`
  в каталоге проекта. Юнит читает их через `EnvironmentFile`.
- **Деплой делает `git reset --hard origin/main` и `rm -rf .next .next-dev`.**
  Всё, что должно пережить деплой, хранится вне каталога проекта.
- Перед коммитом: `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run build`.

## 8. Как проверить, что заработало

1. Локально: `npm run start`, затем расчёт через роут с `provider: "ozon"` —
   должны прийти тарифы, а не `configured:false`.
2. В оформлении заказа выбрать «Ozon, пункт выдачи», ввести город, нажать
   «Рассчитать»: появляются тарифы и список пунктов выдачи.
3. Проверить, что в списке нет тарифов «до двери».
4. Убедиться, что при отсутствии токена сайт не падает, а показывает
   «стоимость сообщит менеджер».
5. Через час работы проверить, что токен обновился сам — это и есть проверка
   пункта про `expires_in`.

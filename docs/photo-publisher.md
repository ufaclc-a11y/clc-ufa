# Публикация фото через Windows CMD

`publish_photos.cmd` остаётся прежним: запускает `python publish_photos.py` из своей папки.
Это публикация **выбранной пачки фотографий**, не синхронизация локального сайта.

## Требования

- Windows с Python 3.10+ в PATH, установленным Tkinter (обычный установщик python.org)
  и Pillow: `python -m pip install Pillow` — один раз, вручную.
- Git for Windows в PATH, настроенные `user.name` / `user.email` и право push в
  `ufaclc-a11y/clc-ufa`. В папке существующего репозитория используется его `origin`
  и имя/почта автора. В отдельной папке без репозитория — HTTPS-адрес этого проекта
  и глобальная конфигурация Git. Авторизация — обычный Git Credential Manager / Git;
  пароль или токен не нужно класть в Python-файлы.
- Node.js 22 в PATH: выполняется только генератор портфолио из свежего main.
  Для самой программы не нужны npm install, Next.js, gh CLI, SSH-доступ к серверу,
  API-токен GitHub или новый Python-пакет помимо Pillow.
- Доступ к GitHub (Git и публичный Actions API), `https://clc-ufa.ru`, свободное место
  для независимой копии репозитория и резервных копий выбранных оригиналов.
  Temp-папка берётся через стандартный `tempfile` (на Windows — пользовательский TEMP).

Проверка установки без публикации:

```cmd
python -c "import tkinter; from PIL import Image, ImageTk; print('Python / Tk / Pillow OK')"
git --version
node --version
```

## Безопасное обновление при локальных коммитах и грязной папке

**Не выполняйте pull, rebase, autostash, reset, clean или push старых локальных коммитов
ради обновления программы.** Не копируйте локальный `data/portfolio-tags.json` на сервер.

1. Закройте старое окно публикации. Сделайте обычную резервную копию всей старой папки,
   особенно `NewPhoto` (включая скрытые `.assignments.json` и `.publisher`, если есть),
   `photo_tags.json`, локальных фото и незакоммиченных файлов.
2. Самый изолированный вариант: распакуйте проверенный архив программы в **новую папку
   вне любого Git-репозитория**, например `D:\CLC-photo-publisher`. Скопируйте в неё
   весь `NewPhoto` и при необходимости `photo_tags.json` из резервной копии. Ничего
   не удаляйте из старой папки и используйте только одно окно/одну рабочую копию фото.
3. Либо замените в прежней папке **только** файлы программы из списка ниже, сохранив
   их старые версии в резервной копии. Не заменяйте `.git`, `data`, `public`, `app`,
   `NewPhoto` или `photo_tags.json`. Локальные коммиты и изменения не мешают новой
   программе: она не коммитит, не стешит и не переключает ваш репозиторий.
4. При переносе уже подготовленной новой пачки сохраняйте **весь** `NewPhoto/.publisher`.
   Адрес `origin` должен остаться тем же. Если раньше был SSH origin, перенос в
   standalone HTTPS меняет адрес: программа остановится, а не потеряет квитанцию.
   В таком случае продолжайте в старой папке с обновлёнными файлами программы.
5. Запустите CMD и убедитесь, что категории/фото на месте. Если прежняя программа
   уже ошибочно убрала оригиналы в `_published` и потеряла разметку, новая версия
   не умеет её угадать: восстановите нужные оригиналы и разметку из резервной копии
   с помощником. Старый локальный коммит сам по себе не является доказательством сайта.

Не изменяйте адрес `origin`, если не уверены, куда он ведёт. Программа предназначена
для этого CLC-проекта; API и проверка живого сайта привязаны к нему.

## Обычная работа и повтор после ошибки

1. Положите оригиналы в `NewPhoto`, откройте CMD и отметьте категории.
2. Нажмите «Опубликовать». Фото без категории остаются на месте. Незнакомый тег
   останавливает новую пачку с пояснением; сервисный «Пропустить» не публикуется.
   Отдельные категории из старого теггера могут не иметь страницы на сайте:
   неизвестная свежему `CATEGORY_META` категория блокируется **до push**.
3. Пачка замораживается в `NewPhoto/.publisher/active.json`: выбранные имена,
   исходные теги, категории, хеши оригиналов, неизменяемые копии и подготовленные
   изображения. Не редактируйте и не удаляйте эту папку до завершения.
4. В независимой временной Git-копии берётся свежий main. Добавляются только выбранные
   новые изображения и недостающие связи с категориями; существующие поля, категории,
   порядок других фото и удалённые на сервере старые файлы не восстанавливаются.
   Генератор запускается там же. Разрешены только фото пачки, JSON-манифест и его
   сгенерированный TypeScript-файл. Неудачный push повторяется не более трёх попыток,
   каждый раз со свежей основой; force push не используется.
5. SHA кандидата сохраняется **до push**, принятый SHA — сразу после. Даже при
   пропавшем ответе Git программа сверяет кандидата со свежим main. Повтор после
   сбоя deploy не должен создавать новый коммит и не требует разметки заново.
   Новые фото не добавляются к незавершённой пачке до её окончания.
6. После push окно ждёт успешное завершение **deploy.yml, push, main, точный SHA**
   (до 20 минут, опрос не чаще раза в 30 секунд). Любая ошибка API, ограничение
   запросов, отменённый/красный workflow или тайм-аут оставляют пачку незавершённой.
   Не нажимайте повтор непрерывно при ограничении API; подождите его восстановления.
   Каждый HTTP-запрос выполняется отдельным короткоживущим процессом того же Python:
   общий абсолютный срок включает DNS, соединение/TLS, заголовки и тело, а не только
   паузы между байтами. По истечении срока процесс принудительно завершается и
   ожидается его выход; сокеты и каналы закрываются до возврата ошибки. Новых файлов
   или пакетов для этого не требуется. Запуск процесса и передача ответа расходуют
   тот же бюджет. Это не гарантия реального времени ОС: создание/завершение процесса
   и планировщик могут добавить задержку; зависание ОС или антивируса не ограничено
   Python. На целевой Windows отдельно проверьте запуск дочернего Python.
7. Затем проверяются прямые `/images/portfolio/<имя>` (байты по SHA-256) и настоящие
   `<img>` в `/portfolio/<категория>` для всех выбранных связей. Один HTTP 200,
   зелёный чужой workflow или просто слово с именем файла в HTML недостаточны.
8. **Только после этих проверок** неизменённые оригиналы копируются в `_published`,
   проверяются и удаляются из входящей папки. Удаляется только исходная разметка
   этой пачки, не чужие записи. Квитанция и копии сохраняются для восстановления.

При ошибке нажмите ту же кнопку повторно: она продолжит сохранённую пачку,
даже если после прерванной архивации в NewPhoto уже нет видимых исходников.
Сообщение об ошибке **не означает, что push не прошёл**. Не размечайте дубли и не
удаляйте квитанцию. Если изменили выбранный оригинал во время публикации, программа
не будет его архивировать: верните именно исходный файл из своей резервной копии
либо обратитесь к помощнику с квитанцией; изменённый файл не будет молча удалён.

### Намеренные ограничения

- Страница категории показывает только первые 48 фото. Публикуйте маленькие пачки
  (не более 48 новых фото на категорию, лучше меньше). Если выбранное уже существующее
  фото находится за первыми 48 или другой push вытеснил фото, проверка остановится
  **без архивации**. Не обходите её удалением квитанции; нужна проверка помощником.
- Смена Pillow/формата может дать другие оптимизированные байты для старого имени.
  Конфликт содержимого под одним именем блокируется, а не перезаписывает удалённое фото.
- Если после принятого push фото/категория удалены на main, повтор не восстановит
  их сам: он остановится для ручного разбора.
- ОС-блокировка не разрешает два экземпляра для одного NewPhoto. После закрытия или
  аварийного завершения блокировка освобождается ОС; файл `.publisher.lock` удалять
  не требуется. Не редактируйте NewPhoto другой программой во время публикации.
- Заполненный/сломанный диск и внезапное отключение питания не дают многофайловой
  транзакции ОС. Квитанция хранит имена архивных копий до удаления оригиналов; при
  обычной ошибке завершения программа возвращает уже убранные исходники и разметку.
  При аварии проверяйте обе папки и квитанцию, не удаляйте резервные копии.

## Состав standalone-архива (для выпуска)

Все файлы берутся **из одного проверенного релиза**, без пользовательских данных:

```text
publish_photos.cmd
publish_photos.py
safe_photo_publisher.py
portfolio_maps.py
photo_tagger.py
docs/photo-publisher.md
```

`photo_tagger.py` нужен для общего списка тегов; отдельно запускать его не требуется.
При первом запуске `NewPhoto` создаётся автоматически. Репозиторий сайта, npm-зависимости,
фото, `.git`, ключи, токены, `.env*`, пользовательские JSON и старые квитанции в архив
программы не включаются. Их пользователь переносит отдельно из своей резервной копии.

Пример сборки архива сопровождающим из корня проверенной копии (не из грязной
папки Windows):

```text
python -m zipfile -c clc-photo-publisher.zip publish_photos.cmd publish_photos.py safe_photo_publisher.py portfolio_maps.py photo_tagger.py docs/photo-publisher.md
python -m zipfile -t clc-photo-publisher.zip
```

## Регрессионные проверки и граница доказательства

```text
python -W error::ResourceWarning -m unittest discover -s tests -p "test_safe_publisher.py" -v
```

Тесты используют только stdlib, локальные bare Git-репозитории и HTTP на loopback;
нужны Git и Node в PATH. Ни реальные фото, ни GitHub/продакшен не публикуются. Реальные
методы GUI исполняются headless через AST без Tk/Pillow, чтобы проверить их связь с
журналом, ошибками deploy/live и архивацией. Этот же запуск включён в CI до npm ci.

**Не заменяет проверку на Windows:** запуск исходного CMD двойным кликом, реальные
Tk-диалоги, Pillow (JPEG/EXIF/прозрачный PNG/WebP), Git Credential Manager/SSH,
PATH и Unicode/длинные пути, блокировка msvcrt, антивирус/блокировка файлов и перенос
архива должны быть проверены на целевой машине. Разрешённая настоящая публикация
с точным Actions SHA и живыми изображениями — отдельный выпускной шаг владельца.
